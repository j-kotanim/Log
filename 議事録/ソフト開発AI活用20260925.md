### 3.2 GitHub Copilot のライセンス／クレジット管理

- 小谷さんが **GitHub Copilot のチーム（情報共有・管理者間連携の場）を作成**したことを共有。
- **契約形態**
  - 村田機械として **NTTドコモビジネス** と契約。村田機械全体で人数分の費用を支払い、その対価として**全社プールのクレジット**を保有。
  - **プールを超過しない限り追加請求は発生しない**前提。
- **部門単位の管理**
  - 全社プールだけでは管理しにくいため、**部門単位で管理者を置く**方針。初期登録として各部門の管理者を登録済み。
  - 部門区分：**L1&A、CFA、繊維、情報、ICC**。それぞれ人数に応じた部門内プールを意識して使う。
  - ある部門が多く使う場合は、**全体を見られる権限者が状況を確認し、他部門と相談して融通する**想定（村田機械全体の枠を超えなければよい）。
- **権限・可視化**
  - **Enterprise 権限**は GitHub 管理者全員が保有。その前提で全体の利用状況を確認できる。
  - 表示軸を切り替えることで、**どの部門がどれだけ使っているかを累積で確認**可能。**コストセンター単位**での確認も話題に上がった。
  - 個人単位では、VS Code 拡張機能 **Copilot Credit Meter** で自分の使用量を確認できる。
- 情報共有の運営面では、**村上さんに情報共有の広め役を担ってもらえないか**という相談があった。

### 3.4 第1グループ：USDM／機能仕様書の自動生成

- テーマは **構想設計から機能仕様書を作る**こと。遠藤さん側のテーマ（課題一覧から変更対象を作る）と流れが似ていると整理された。
- **入力情報**：マインドマップ、全体イメージのPowerPoint、製品仕様書など。
- **入力ファイル変換の知見**
  - PowerPoint はそのままでは読ませにくいため **PNG化**。
  - Excel は **CSV化**。
  - Markdown はテキストなので扱いやすい。
- **生成プロセス（段階化）**
  1. 構想設計から機能一覧を作る
  2. 人がレビューしながら項目を洗い出す
  3. USDMベースの要求へ展開し、**要求内容・必要理由・出典付き**で仕様化する
- **進捗**
  - USDMベースの要求書は、要求内容・理由・出典付きの形で項目ごとにできてくる状態まで到達。
  - ただし **テキストベースでは進んでいるが、まだExcelには落とせていない**。
- **認識の共有**
  - 「いきなり最終成果物を出させるのは無理」であり、**中間成果物を置いて人間が壁打ち・レビューする前提**が重要。
  - GitHub上で進める場合は、**フォルダ構成・参考資料・お手本・プロンプト集を整理して再現可能にする**。
  - ゴールは小谷さん個人ができることではなく、**「みんなができる」状態にすること**。
- 次回、**できたものを改めて提示する**方向。

### 3.5 第2グループ：Zendesk導入評価・規格対応・Jitera活用

- 月次シート上の項目は **Zendesk評価**（※聞き取り推定）と **ICC・EC・繊維への聞き取り**。
- **規格対応**
  - AIツール導入にあたり「AIを入れるならこの規約に沿う必要がある」と指摘され、**ISO 27001系**の対応が論点に（※書き起こし不鮮明、ISO/IEC 27001 と推定）。
- **導入評価の状況**
  - 現時点では **導入評価自体がまだ十分に進められていない**。
- **納入仕様書から変更対象一覧を作るテーマ**
  - ①納入仕様書ベースの課題一覧 → ②カスタマイズ一覧 → ③プログラム単位のカスタマイズPG一覧、の3段階がある。
  - **どこまでをAIにやらせるかは未決**。
- **Jitera（ジテラ）のクレジット問題**
  - クレジット不足が課題。追加枠を一度無償で付けてもらったが**すでに使い切っており、現状は使えない**認識。契約上も「グレー」と表現。
  - 利用状況を見ると、**上位3〜4人程度のヘビーユーザーが使い切っている**状況。まず使い方のヒアリングが必要。
  - 対応案として「枠を増やす」「組織単位に上限を設ける」「第2グループ用に一定枠を確保する」などが議論されたが**未決定**。
  - **第2グループは試用段階、第3グループは実務で本格利用**という温度差があり、**試用が実務を止めてはいけない**という懸念が共有された。
  - 10月からJitera側で試せる方向に道を作る流れになっており、まずは「何ができるか」「変更対象リスト作成でどう使うか」を検討する。

### 3.6 第3グループ：稼働分析ダッシュボード・UIモック

- 月次シート上は **稼働分析ダッシュボードを開発中**。
- 詳細議論の中心は **UIモック作成**（髙田さん中心 ※聞き取り推定）。
  - AIで新機能の画面モックを作る取り組み。
  - ただし単にAIへ投げると**好き勝手な画面**ができるため、**デザインガイドと部品群（コンポーネント）を先に作り、その部品を組み合わせてモック生成させる**方針。
- **狙い**
  - ステークホルダーに実際に触ってもらい、**手戻りの少ない開発にする**こと。
  - 静止画だけでは見抜けない業務上の不足（検索条件、項目漏れ、現場端末での使い勝手など）を早期に発見する。
- **Figma について**
  - **工数が重すぎる**ため主戦場にしない認識。ICCでも運用できているプロジェクトは限られる。
  - MCP による活用可能性にも言及。
- **成果の定義**
  - 「髙田さん個人のスキル」ではなく、**部品化＋デザインガイド＋入力方法として仕組み化できること**が重要。
- 現状は **GMIS（ジーミックス）中心**で、他領域は未着手。
- マニュアルについては、製品仕様のスコープにソフトだけでなくマニュアルも含まれる旨の言及があったが、進捗の深掘りはなし。

### 3.8 課題・懸念

- Copilot・Jiteraともに、**一部のヘビーユーザーがクレジットを使い切ると他の人が使えなくなる**。
- Excel／PowerPoint／画像など、**AIにそのまま渡しにくい入力形式が多い**。変換前提の運用が必要。
- AIにいきなり最終成果物を出させるのは難しく、**中間成果物＋人によるレビュー**が必要。
- UIモックは、制約を与えないと**デザイン不統一・実装不能な案**が出る。
- Figma は工数過大。**軽量な代替手段でどこまでいけるか**が論点。
- 第2グループは **規格対応・導入評価・Jitera枠不足**が重なり、前に進みにくい。

## 4. 決定事項

1. GitHub Copilot は、村田機械全体契約のクレジットプールを前提に、**部門単位の管理者運用**で回す。
2. 実施計画（月次シート）は、**月末時点で「予定」ではなく「実績」を残して締める**。
3. 第1グループは、構想設計 → 機能一覧 → USDM要求 → 機能仕様書の**段階生成＋人レビュー**路線で進める。
4. 第2グループは、Jiteraが使えるようになった段階で、**変更対象リスト作成に何が使えるかを評価**する。
5. 第3グループは、**デザインガイド作成とモジュール部品作成**を軸に進める。
