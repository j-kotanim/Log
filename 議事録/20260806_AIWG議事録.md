## 3. 主要議題

### 3.1 GitHub Copilot / コパイロットの活用

- Copilotの使用感は従来と異なり、結論・構造をすぐ返してくれる点が便利との評価。まだ使い慣れないという声も。
- 別ツールとの比較で、Copilotの方が一貫して使いやすいとの意見。
- 音声・プログラムのコーディング領域でも全体的に活用可能。
- ライセンスは約30名分（マックス30ライセンス）。全員が常用しているわけではなく、必要に応じて未使用者を洗い出し再配分する運用。ICCメンバー・外注先にも貸与実績あり。
- ライセンス1個追加での著作継承・レベル感の検証要望あり。
- ドキュメントの制限（ソース参照の範囲）に注意が必要。高精度モデル利用時は1スレッドでも入力コストが重くなる。

### 3.2 リポジトリ／プロジェクト管理

- GitHubのリポジトリ構成案: **インプット / アウトプット / リファレンス / ドック** の4フォルダ体制。
  - インプット: 構想設計・製品仕様など元情報
  - アウトプット: 生成物
  - リファレンス: 参照資料
- 案件（プロジェクト）単位でブランチを切る運用、リポジトリに使用書・設計書を投入して開始する方式を検討。
- ディレクトリ構造は体系的に管理でき、プロジェクト単位運用が有効との判断。
- ソースコード管理はジテラ（ツール）が担当、ナレッジ活用作業はジテラが得意との整理。
- CSV変換して保存する運用（1タブ＝1ファイル）も検討。過渡期のため要検証。

### 3.3 画面設定書・自動化

- 画面設定書の自動化は完了（設定で全画面を作成可能）。顧客向け設定は属人的だったが、データベースから引用してエクセルデータを作成する自動化をほぼ実現。
- Pythonの普通に組まれたソース／スクリプトも利用可能。
- 今後: 設定書からDVD電子（帳票・図面等）を自動生成する方向を検討。
- ボカブ向けのカスタマイズ設定仕様書は顧客側で作成されるケースがある点に留意。
- 年末までのDVD完了を目標に、EDIプロジェクトの情報とも連携。

### 3.4 テスト自動化

- 検索条件・検索フィールドの設定からテスト項目が自動生成できる見込み。設定を作れば検索フィールドに項目が出る仕組み。
- テスト手順書の自動作成ツール（シナリオ生成）を検討。シナリオ生成自体は可能だが、手を貸す部分が大きなテーマ。
- 課題: **製品知識がないとテストできない／結果が判断できない**。計算結果の検証が最大の難所。
- 単体テスト・結合テストは全部動いており、総合テストの必要性を含め検証範囲を議論。
- 環境準備・前提手順もテスト実行前に必要。実機テスト時の交番ごとの手順・確認欄を書き出し、結果を出す形に。

### 3.5 要求仕様書／機能証書の自動生成

- 要求証書からは要求収書が作れない（情報不足）という課題認識。
- 構想設計から機能証書を作る流れを整理: **インプット情報 → 構想設計 → 機能概要 → 製品仕様 → 機能証書**。
- USDM形式での記述を採用。大きな要求・大きな仕様がまず先にあり、次に中軌道の仕様、小機能の使用がある、という粒度で書き下す方針。
- 機能項目を「USDMの収書」として作成し、大きな項目から詳細化していくことでモレの発見を早期化できる。
- 非機能要件も入れないとパフォーマンスが落ちるため、その辺も含める。
- AIが機能コンクを一般的に必要とされる観点で補完し、抜けがないかプロンプトで確認させる案。

### 3.6 AI活用の全体像

- 「AIが作る」だけでなく、**人が考えて作る**部分を残す。人とAIがまずドラフトを作り、機能維持・レビューを回す。
- 昨日のドラフト→翌日レビューという流れを、USDMに合った粒度で回していく。
- 必ずゲートを通す運用とし、メンバー全体でレビューするチームデビューを1回実施。
- AIはフェーズの叩き台に使う。人によって出来が変わらないよう標準化する狙い。
- 漏れが出た場合はAIに投げ、AIが返した内容をデビューして再度プログラムを回す。混乱が生じたら都度整理。

## 4. 決定事項

1. 第2四半期は、第1グループ＝新情報アップデート、第2グループ＝実践と共有、第3グループ＝第1・第3で方向性決定、で進める。
2. 意見・コメントは必ず出す（宿題ベースで進行、この場で決定する）。
3. 画面設定書の自動化は完了とし、次はDVD／電子帳票の自動生成に着手。
4. リポジトリはインプット／アウトプット／リファレンス／ドックの4フォルダ構成で構築し、案件単位で運用。
5. 要求仕様はUSDM形式で記述する。
6. Copilotライセンスは未使用者を洗い出し、必要な人へ再配分する。
7. 成果はGitHub上でリポジトリ管理し、次回レポートで結果を共有する。
