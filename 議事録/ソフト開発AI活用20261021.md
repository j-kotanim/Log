### 3.5 第1グループ：USDM／機能仕様書生成と GitHub 運用

#### 成果物・作業環境の整備

- ローカルでAIと壁打ちして作成した仕組みを、情報側の GitHub リポジトリへ展開。
- 開発ソースの既存リポジトリとは分け、**USDM用リポジトリ**として整備。
- リポジトリ構成、作業方法、説明会資料などを用意。
- **基本の成果物は Markdown で管理し、最終的に Python で Excel へ変換**する流れ。
- Python を使える人はローカルPCで変換、使えない人は **Codespaces** を利用する運用。

#### 段階生成と人による承認

- フェーズ0〜5の段階的な進め方を説明。
  - **フェーズ0**：入力情報を準備し、入力用フォルダーに格納
  - **フェーズ1**：AIが入力資料から機能項目を洗い出す
  - **フェーズ2**：人がレビューし、何を作るかを確定
  - **フェーズ3〜5**：確定した項目に対して理由付け・仕様展開を進める
- **フェーズ2・5を人によるゲート**として設け、承認がそろうまで次段階へ進まない構成（※承認対象者の範囲は聞き取り推定）。
- AIには、**根拠のない仕様を追加せず、事実に基づいて記載する**よう求める。
- 入力資料と作業中成果物を分けるフォルダー構成を採用。

#### Office文書・PDFのMarkdown変換

- **SharePoint と Power Automate** を用いた文書のテキスト化・Markdown化を実演。
- 「変換前」「変換結果」のフォルダーを設け、フローから変換する。
- PDF はテキスト抽出、Office文書は別処理と、形式ごとに分岐。
- Markdown化後は GitHub 側のAI処理に渡しやすくなる。
- 現時点ではソフトチームのメンバーを利用者登録。必要な人への共有・利用拡大も可能。
- 変換結果の確認・コピー・削除が利用者任せになるとファイルが蓄積する懸念あり。フローの閲覧権限もその場では未確定。

#### B3F での実案件試行

- B3F の資料を入力し、フェーズ別のサンプルプロンプトで機能項目一覧を生成。
- 現時点の一覧は粗く、**詳細な製品仕様書が未完成・未投入で、構想設計中心の入力にとどまることが原因**と説明。
- 漏れを成果物側で修正するより、**入力情報を補強する方がよい**のではないかという意見。
- 次はリーダーへのワークショップを行い、人レビューで機能項目一覧を完成させる予定。
- フローを最後まで通す確認は行っているが、**実案件で最終的に十分な品質の仕様書ができるかは未確認**。

#### GitHub でのレビュー・展開

- 作業ブランチで生成・修正し、**プルリクエストでレビュー**する。
- **main ブランチは保護**し、直接変更できず、PRからのマージでのみ更新する設定。
- この運用には、成果物の管理だけでなく、メンバーに **PR・承認・マージを習得してもらう狙い**もある。
- 他部署はリポジトリをコピーして利用可能。運用ポリシーは利用側で調整できる。
- 個人アカウントのリポジトリへ複製する場合は、**誤って公開しないこと**を注意喚起。
- TortoiseGit、Git Extensions 等のローカル操作と、Web上のPR・ワークフロー操作の使い分けも共有。
- 森野さん側では、人と Copilot の両方が作成したPRを扱い、main を直接変更しない運用を一部実施中と紹介。

#### 工程の省略・レビュー観点

- 機能項目が既に定まっている案件では、その一覧をテキストで入力し、途中の段階から進められる。
- 入力の書式は必ずしも提示したサンプルと同一である必要はない。
- 人レビュー用の**チェックリスト**も整備。粒度、入力情報との対応、出所の明確さなどを確認。
- 一方、AIが大量のドキュメントを生成するため、**人が読み切れるか、実際に使ってもらえるか**が課題。

### 3.6 第2グループ：Jitera による変更対象プログラム一覧の生成

#### 取り組みの目的・対象範囲

- 顧客ヒアリングから作成した納入仕様書を基に、開発へ渡す**変更対象プログラム一覧**を作る作業に時間がかかっている。
- Jitera は GMIS のリポジトリと接続しソースを参照できるため、カスタマイズ対象の抽出に活用できないかを評価。
- 一足飛びの生成は難しく、当面は**人が整理した課題・カスタマイズ情報から、最終段階のプログラム一覧を生成する部分**を中心に試行。
- 納入仕様書から中間の一覧を作る工程は引き続き検討。

#### Jitera に持たせた情報

- データベース定義書（テーブル・項目）
- データベースの関連図
- モジュールごとの機能説明
- モジュール一覧
- ソースIDとモジュールIDの対応、命名規約
- 実案件の設計資料・納入仕様書・課題一覧 等

Jitera では Office文書をそのまま投入できる点も紹介された。第2グループの報告は遠藤さん中心とみられる（※聞き取り推定）。

#### 実験方法と結果

既存案件について、人が作成済みの変更対象プログラム一覧を比較対象とし、Jiteraの出力とプログラムID等で Excel 上で照合。入力資料・説明を段階的に追加して改善を確認した。

| 試行 | 主な入力・補足 | 会議で説明された結果 |
|---|---|---|
| 1回目 | 課題一覧を中心に投入 | 約6.36点。一致が少なく、不要とみられる候補も出力 |
| 2回目 | システム化方針、全体図、外部設計、補足資料等を追加 | 約34点 |
| 3回目 | AIが誤解した業務・機能の説明を補足 | 40点前後への言及あり（※値は聞き取り推定） |
| 4回目 | 別のモニター画面情報、人が分析した修正内容等を追加 | 未採点 |
| 5回目 | さらに分かりやすくするよう指示 | 約54点 |
| 6回目 | 修正対象プログラムに関する規約・コード上のルールを補足 | 約72点、概ね7割（※72は聞き取り推定） |

- この点数は**今回の比較用一覧との一致を評価したもの**であり、一般的な精度を示すものではありません。
- 正解総数・集計単位の説明にも不鮮明な箇所があり、厳密な採点式・適合率・再現率までは確定できません。

#### 評価で分かったこと

- **背景資料・規約を渡すほど結果が改善する。**
  - 課題一覧の短い表現だけでは、業務上の意味や具体的な修正方法が伝わらない。
  - 人が判断する際に参照している資料も、AIへ渡す必要がある。
- **人が作った「答え」も、入力資料と完全には一致しない。**
  - 顧客との会話だけで追加された依頼があり、納入仕様書に記載されていない。
  - 逆に、資料には納品書の修正が書かれているのに、人の最終一覧には載っていない例があった。
  - 途中の仕様変更・不要化の経緯が追えない場合、単純比較だけでは誤りと断定できない。
- **過剰抽出の内容は引き続き分析が必要。**
  - 本当に不要なのか、人が見落とした必要な修正なのかを確認する。
  - 候補として出した後に、人が実施要否を判断する考え方も議論された。

#### 次の進め方

- GMIS の業務・機能を説明する**事前ナレッジ**を整備する。
  - 既存の人向け説明資料を活用。
  - ソースからしか分からない情報は、あらかじめ解析してドキュメント化。
  - 人が内容を確認し、期待した説明になっているかを評価する。
- **プログラムID・名称の一覧**も渡し、毎回ソースを探索させる負担を減らす。
- 強いナレッジができれば、納入仕様書から直接変更対象を抽出し、中間一覧の作成を省ける可能性もある（※現時点では将来案）。
- 機会があれば実案件で試し、リーダーにも結果を共有して協力を得る。
- 変更箇所が分かれば、そのままコード生成まで進めたいという発展案も出た（実施決定・検証済みではない）。

### 3.9 課題・懸念

- **入力情報の不足・品質**：構想設計だけでは機能項目が粗くなる。業務用語、プログラム対応、規約など暗黙知を補う必要がある。
- **評価用の正解データの整合性**：口頭依頼、途中変更、資料の更新漏れが混在し、AIの誤りと資料不足を切り分けにくい。
- **変更対象の漏れ・過剰抽出**：人の一覧と異なる候補が、不要なのか有益な指摘なのかを確認する必要がある。
- **生成後の品質保証**：フローが最後まで動くことと、実案件の仕様書として正しいことは別。AIによる連続修正で既存動作が破壊される問題もある。
- **人のレビュー負荷・利用定着**：ドキュメントが増えすぎると読めない。手順整備だけでなく PR・承認・マージの習得が必要。
- **費用・時間**：高コストモデルの常用や、毎回のソース探索がクレジットを消費する。

- **第3グループの成果の仕組み化**：モック数の増加と、共通ガイド・再利用部品の整備を区別して追う必要がある。
